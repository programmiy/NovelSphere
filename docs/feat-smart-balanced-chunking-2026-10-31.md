# 사전 전수 계획 기반 스마트 동적 균형 청킹 엔진 도입 (2026-10-31)

## 1. 배경 및 목적
- 기존 순차 탐욕(Greedy) 청킹 방식은 누적 1,300자 이상에서 45문장에 도달하면 즉시 청크를 절단하여, 50~55문장 회차나 100~105문장 회차에서 마지막 묶음에 5~14문장의 소량 자투리 청크(`45+8`, `45+45+15` 등)가 빈번하게 발생했습니다.
- 이로 인해 불필요한 추가 API 호출, RPM 쿼터 차감, 묶음 간 쿨다운 대기 지연이 발생하던 비효율을 제거하면서도, 무리한 청크 비대화로 인한 `verbatim` 역소모·출력 토큰 절단·MV3 타임아웃 등의 부작용을 모두 차단하기 위해 **사전 전수 계획 기반 동적 계획법(Constrained Optimal Partitioning DP) 균형 청킹 엔진**으로 전면 개편했습니다.

---

## 2. 반영된 10대 안전·성능·효율 설계 사항

1. **스위트 스폿 원샷 흡수 (`CHUNK_SINGLE_SHOT_MAX_CHARS = 1850`, 서술문 54개 ~ 대화문 74개)**:
   - 어텐션 저하(`verbatim` 단건 복구 역소모)가 발생하지 않는 안전 스위트 스폿 내 분량은 자투리로 쪼개지 않고 단 1묶음으로 원샷 완결합니다.
2. **제약 조건부 최적 분할 DP (`solveBalancedPartition`)**:
   - 2묶음 이상일 때 `45+12`나 `45+45+15` 대신 최적 묶음 수 $K$를 도출하고 글자 수(65%) + 문장 수(35%) 복합 가중치 편차 제곱합을 최소화하여 `28+32`, `50+55`, `33+36+36`처럼 균등 분배합니다.
   - 만약 편중된 문장 분포로 목표 $K$에서 하드 상한 준수가 불가능하면 자동으로 $K+1$ 증분 탐색을 수행하여 100% 해를 보장합니다.
3. **문장 길이 편차(Skewness) 방어**:
   - 전반부 장문 서술 + 후반부 단문 대화 같은 극단적 비대칭 구조에서도 모든 다중 문장 청크가 하드 상한(2,000자 / 75문장)과 소프트 탄성 경계(1,840자)를 철저히 준수합니다.
4. **단일 거대 문장(Outlier $\ge$ 1,400자) 사전 격리**:
   - 줄바꿈 없는 초장문 단락이 인접 일반 문장의 평균과 예산을 오염시키지 않도록 사전에 독립 청크로 격리하고 앞뒤 연속 세그먼트를 각각 최적 분할합니다.
5. **자연 경계 스내핑 (Natural Boundary Snapping)**:
   - `isDialogueLine` / `isSceneBreakLine`을 통해 연속 대사(`「...」` 티키타카) 한복판 절단에 페널티를 부여하고, 장면 전환 기호(`◇`, `***`, `――`) 및 대사 종료 직후 서술문 전환 지점에 보너스를 부여하여 화자 말투(존비어)·호칭 일관성을 보호합니다.
6. **실시간 열람 체감 속도(TTFB) 가속**:
   - 다중 묶음 시 첫 번째 청크의 목표 비중을 `0.92`배로 살짝 가볍게 배분하여 상단 첫 한글 렌더링 응답 시간을 앞당깁니다.
7. **재번역 상위 모델(`isRetranslation: true`) 비대칭 보호**:
   - `gemini-3.8-flash` 호출 시 상위 모델의 레이턴시 및 503 과부하 방어를 위해 글자 수(1,750자 하드 / 1,550자 소프트) 및 문장 수(최대 60개) 상한을 자동 보수화합니다.
8. **JSON 구조 출력 토큰 팽창 방어**:
   - 원샷 판정 및 다중 분할 시 문장당 JSON 키·이스케이프 오버헤드 여유 마진을 확보하여 `MAX_TOKENS` 응답 절단을 예방합니다.
9. **마지막 청크 미완료 빈칸 합류(`selectSafePiggybackItems`) 오버플로우 캡 가드**:
   - `page_translator.ts`에서 마지막 청크에 이전 미완료 빈칸(`emptyItems`) 합류 시 2,000자 및 68문장 상한 이내 항목(`fitted`)만 태우고, 초과분(`deferred`)은 최종 보완 꾸러미로 안전 이관합니다.
10. **최종 보완 꾸러미 안전 청킹**:
    - `remainingEmptyItems` 보완 실행 시에도 `createBudgetChunks`를 적용하여 대량 잔여분 발생 시에도 단일 요청 과부하를 원천 차단합니다.
